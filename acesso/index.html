Acessos registrados durante uma queda podem ser recuperados.

Investigação da API e dos manuais oficiais do Control iD iDFace Max para determinar como extrair entradas de associados realizadas enquanto o equipamento esteve sem comunicação com o backend.

Ver solicitação ao fornecedor → Procedimento de recuperação
Resposta objetiva
Sim, com condições.

O terminal persiste eventos em access_logs. Depois da reconexão, os dados podem ser lidos pela API, exportados em CSV/USB ou coletados pelo iDCloud via Push.

Conclusão

O dado existe antes de chegar ao backend.

A indisponibilidade do backend não implica, por si só, perda do histórico. A arquitetura do produto prevê operação local e posterior acesso aos registros — desde que a contingência estivesse habilitada, os cadastros estivessem sincronizados e os logs ainda não tenham sofrido rotação ou exclusão.

✓

Conclusão técnica: recuperação viável

Para um período já ocorrido, a fonte mais confiável é a tabela local access_logs. Para a operação futura, recomendamos combinar eventos em tempo real com uma reconciliação por cursor, usando a chave composta (device_id, access_log.id) para impedir duplicidades.

01

API direta no terminal

Login em /login.fcgi e leitura paginada de access_logs por /load_objects.fcgi.

02

Exportação independente

A interface embarcada e a porta USB permitem gerar um pacote de logs, útil como evidência bruta e contingência.

03

iDSecure / iDCloud

O modo Push permite ao serviço remoto executar comandos no equipamento e disponibilizar logs pela internet.

Como funciona

Queda, contingência e reconexão.

Nos modos Online Pro/Enterprise, o equipamento tenta falar com o servidor. Com contingency_enabled = 1, falhas consecutivas fazem o terminal recorrer à base local. O pedido device_is_alive informa quantos logs estão disponíveis quando tenta voltar ao modo online.

Estado normal

Terminal online

Identificação e autorização seguem o modo configurado, com comunicação ativa com o servidor.

Falha

Backend indisponível

Após o limite de tentativas e timeout configurados, o equipamento detecta a perda de comunicação.

Contingência

Validação local

Usuários, credenciais e regras já sincronizados são usados localmente; os eventos entram em access_logs.

Retorno

Reconciliação

Ao reconectar, o histórico local pode ser consultado, exportado e incorporado ao banco central.

O que fica disponível

  • id único do log no equipamento
  • time em Unix timestamp
  • event: concedido, negado e outros resultados
  • user_id, device_id, portal e identificador

Condições necessárias

  • Contingência habilitada no modo online
  • Usuários e regras presentes na base local
  • Relógio e fuso do terminal corretos
  • Logs ainda preservados no armazenamento

Limites da evidência

O que ainda precisa ser confirmado.

A documentação é suficiente para comprovar a possibilidade técnica, mas não publica todos os detalhes operacionais da versão de firmware e do plano iDSecure contratado pelo Recreio.

Não presumir reenvio do Monitor

O Monitor publica alterações em tempo real para /api/notifications/dao, mas a documentação pública não promete fila durável nem reenvio integral após uma queda. Webhook não substitui reconciliação.

Retenção exata não publicada

O fabricante não informa o limite da tabela access_logs do iDFace Max. O limite de 25 mil encontrado no manual refere-se a logs de auditoria — não aos acessos.

Backfill do iDSecure é uma caixa-preta

O protocolo Push suporta a coleta, mas o manual Cloud não descreve cursor, tentativas ou algoritmo interno de recuperação histórica. Precisamos de confirmação do fornecedor.

Extração direta reduz o risco

Mesmo se a sincronização automática não completar, a leitura local e a exportação CSV oferecem uma rota independente para preservar e reconciliar os eventos.

Incidente já ocorrido

Procedimento seguro de recuperação.

A ordem importa: primeiro preservar, depois atualizar ou alterar o equipamento. O objetivo é produzir um conjunto bruto auditável e uma carga deduplicada para o backend.

01

Congelar mudanças destrutivas

Não resetar, limpar logs, restaurar backup nem atualizar firmware antes de extrair uma cópia.

02

Inventariar cada equipamento

Registrar serial, device_id, IP, modelo, firmware, data/hora, fuso e intervalo da indisponibilidade.

03

Delimitar o buraco no backend

Anotar o último evento antes da queda e o primeiro depois da reconexão, sempre por dispositivo.

04

Extrair pela API local

Ler access_logs em páginas ordenadas por id; consultar users para resolver nome e matrícula.

05

Gerar evidência independente

Exportar também logs.zip/logs.csv pela interface ou USB e preservar o arquivo original sem edição.

06

Conciliar e validar

Deduplicar por (device_id, log_id), converter horário corretamente e comparar amostras entre anotação, equipamento e iDSecure.

Antes de começar

Checklist para preservar valor probatório e reduzir risco de perda.

  • Salvar configuração e versão atual
  • Usar rede de gestão/VPN
  • Preferir HTTPS se habilitado
  • Não usar senha padrão
  • Guardar arquivos brutos com hash
  • Documentar quem fez a extração
  • Validar uma amostra com a portaria
Referência rápida

Chamadas mínimas da API.

Exemplos ilustrativos para execução na rede local do terminal. Credenciais reais e sessões não devem ser compartilhadas por e-mail, chamado ou documento.

1. Criar sessão
POST /login.fcgi
Content-Type: application/json

{
  "login": "USUARIO_ADMINISTRATIVO",
  "password": "SENHA"
}
2. Ler por cursor
POST /load_objects.fcgi?session=SESSAO
Content-Type: application/json

{
  "object": "access_logs",
  "limit": 1000,
  "offset": 0,
  "order": ["id", "ascending"],
  "where": {
    "access_logs": {
      "id": {">": 123456}
    }
  }
}

Regra de ingestão recomendada

Persistir o maior id confirmado por equipamento somente depois que a gravação no banco central terminar. Reprocessamentos devem ser idempotentes pela chave (serial ou device_id, access_log.id). Para entradas efetivamente concedidas, filtrar event = 7, mas preservar também negados (event = 6) para auditoria.
